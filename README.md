#### Видеоконтент (порядок величины)

Для оценки объёма видеобиблиотеки используется:
- около `80 000` единиц контента [^6]
- диапазон средней длительности одной единицы контента: `45–90 минут`  
  (единица контента включает фильмы, серии и другие типы контента)
- в качестве ориентира по ABR-профилям — пример HLS bitrate ladder из AWS:  
  `7.8, 6, 4.5, 3, 2, 1.1, 0.8, 0.4, 0.2 Mbps` [^5]

Суммарный битрейт набора ABR-профилей:
- `7.8 + 6 + 4.5 + 3 + 2 + 1.1 + 0.8 + 0.4 + 0.2 = 25.8 Мбит/с`

Размер одной единицы контента:
- при 45 мин:
  - `25.8 Мбит/с × 2700 с / 8 ≈ 8.71 ГБ`
- при 90 мин:
  - `25.8 Мбит/с × 5400 с / 8 ≈ 17.42 ГБ`

Общий объём видеобиблиотеки:
- при 45 мин: `80 000 × 8.71 ГБ ≈ 697 ТБ`
- при 90 мин: `80 000 × 17.42 ГБ ≈ 1 394 ТБ ≈ 1.39 ПБ`

Итого порядок объёма видеоконтента:
- **`~697 ТБ – 1.39 ПБ`**

### Прирост дискового пространства

Для планирования ёмкости хранилищ оценивается годовой прирост по основным категориям данных:
- видеоконтент,
- пользовательские данные,
- постеры/изображения.

#### Прирост пользовательских данных

По данным Кинопоиска, в 2025 году количество смотрящих подписчиков выросло на **29% год к году**[^1].

Оценим размер аудитории годом ранее:
- `18 000 000 / 1.29 ≈ 13 953 488`

Тогда прирост смотрящих подписчиков за год:
- `18 000 000 - 13 953 488 ≈ 4 046 512 пользователей`

При среднем размере пользовательских данных `24 КБ` на пользователя годовой прирост пользовательских данных составит:
- `4 046 512 × 24 КБ ≈ 97 116 288 КБ ≈ 97 ГБ`

#### Прирост видеоконтента

- **80 тыс. единиц контента** (2020) [^6];
- около **100 тыс. единиц контента** (2023) (данные были упомянуты вскользь и без точных цифр) [^7].

Оценка среднего прироста по количеству единиц контента:
- `100 000 - 80 000 = 20 000` единиц контента
- период между публикациями: примерно `3 года`
- `20 000 / 3 ≈ 6 667` единиц контента в год

Тогда годовой прирост видеохранилища составит:

- при 45 мин:
  - `6 667 × 8.71 ГБ ≈ 58 077 ГБ ≈ 58.1 ТБ/год`
- при 90 мин:
  - `6 667 × 17.42 ГБ ≈ 116 153 ГБ ≈ 116.2 ТБ/год`

#### Постеры/изображения

- минимальная оценка:
  - `6 667 × 0.5 МБ ≈ 3 333.5 МБ ≈ 3.3 ГБ/год`
- максимальная оценка:
  - `6 667 × 1 МБ ≈ 6 667 МБ ≈ 6.7 ГБ/год`

### Схема DNS-балансировки

Для выбора ближайшего или наиболее подходящего ДЦ используем **latency-based DNS** в сочетании с **Weighted GSLB**:

- клиент обращается к домену (`www`, `api`, `img`, `static`);
- DNS определяет подходящий регион;
- с учётом весов, health checks и доступности возвращается IP нужного ДЦ;
- используется короткий TTL (`30–60 сек`) для ускоренного переключения при аварии.

DNS-балансировка подходит для:
- `www.kinopoisk.ru`
- `api.kinopoisk.ru`
- `img.kinopoisk.ru`
- `static.kinopoisk.ru`

### Схема Anycast-балансировки

Для видеотрафика (`cdn.kinopoisk.ru`) целесообразно использовать **BGP Anycast** на edge-уровне CDN:

- один и тот же IP анонсируется из нескольких точек присутствия;
- пользовательский трафик направляется в ближайшую точку по маршрутам BGP;
- это снижает задержку и ускоряет старт загрузки видео-сегментов;
- далее внутри выбранного региона запрос обслуживается локальным CDN-кэшем или сервером.

### Механизм регулировки трафика между ДЦ

Для управления нагрузкой между ДЦ используется:

1. **Весовая DNS-балансировка (Weighted GSLB)**  
   Позволяет менять долю входящего трафика по ДЦ, например при плановых работах или частичной перегрузке площадки.

2. **Health checks**  
   При деградации или отказе ДЦ он автоматически убирается из DNS-выдачи для новых клиентов.

3. **Failover в соседний регион**  
   Запросы перенаправляются в ближайший по задержке ДЦ:
   - Москва ↔ Санкт-Петербург
   - Москва ↔ Ростов-на-Дону
   - Екатеринбург ↔ Новосибирск
   - Владивосток ↔ Новосибирск

4. **Плавное снижение веса при плановом выводе ДЦ**  
   Если площадку нужно временно отключить, её вес постепенно уменьшается до нуля, после чего она исключается из DNS-выдачи.

## Часть 4. Локальная балансировка нагрузки

### Схема локальной балансировки

Внутри дата-центра локальную балансировку Кинопоиска целесообразно разделить на два контура:

1. **Web/API**:
   - `www.kinopoisk.ru`
   - `api.kinopoisk.ru`
   - `img.kinopoisk.ru`
   - `static.kinopoisk.ru`

2. **CDN**:
   - `cdn.kinopoisk.ru`

Для **Web/API** используется схема:

`Клиент → L4-балансировщик → L7-балансировщик → backend-сервисы`

- **L4** распределяет TCP/TLS-соединения между L7-узлами; возможные реализации — **LVS** или **HAProxy** в TCP-режиме; резервирование — **N × 2**.
- **L7** выполняет **SSL терминацию** и HTTP-маршрутизацию; возможная реализация — **NGINX**; резервирование — **N + 1**.

Для **CDN** используется отдельный контур:

`Клиент → локальное распределение → CDN cache node → origin (при cache miss)`

Это связано с тем, что для API и web-трафика важны SSL терминация и L7-маршрутизация, а для видеотрафика CDN основным ограничителем является сетевая пропускная способность.

### Расчёт количества балансировщиков для web/API-контура

Расчёт выполним для наиболее нагруженного дата-центра — **Москвы**.  
Из части 3:

- общий пиковый **API RPS**: `31 851.11`
- общий пиковый **API-трафик**: `~2.04 Гбит/с`
- доля Москвы: `45%`

Тогда для Москвы:

- `31 851.11 × 0.45 ≈ 14 333 RPS`
- `2.04 × 0.45 ≈ 0.92 Гбит/с`

### Выбор производительности одного L7-узла

Для сервера уровня **16 CPU** в тестах были получены следующие значения [^8]:

| CPU | HTTPS RPS | SSL TPS | Throughput |
|---|---:|---:|---:|
| 16 | 341 232 | 54 877 | 8.80 Гбит/с |

Так как после 16 CPU прирост производительности замедляется, в качестве базового L7-узла принимаем:

- **CPU 16 cores**
- **NIC 10GbE**

### Расчёт числа L7-балансировщиков

Проверим два ограничителя:

1. **по HTTPS RPS**  
   `N_rps = 14 333 / 341 232 ≈ 0.042`

2. **по сети**  
   `N_net = 0.92 / 8.8 ≈ 0.105`

В обоих случаях достаточно **1 активного узла**.  
С учётом резервирования по формуле **N + 1**:

Итого:

- **L7-балансировщики: 2 узла**

### Расчёт числа L4-балансировщиков

Для московского web/API-контура требуется всего `~0.92 Гбит/с`, поэтому одного активного L4-узла с интерфейсом **10GbE** достаточно.

С учётом резервирования по формуле **N × 2**:

Итого:

- **L4-балансировщики: 2 узла**

### Расчёт CDN-контура

Для Москвы из части 3 ранее было получено:

- **пиковый CDN RPS:** `~60 000`
- **пиковая полоса CDN:** `~1080 Гбит/с`

Для CDN главным ограничителем является именно **сетевая полоса**. В качестве базового cache/edge-сервера примем узел с интерфейсом **100GbE**.

Тогда число активных CDN-узлов:

- `N_cdn = 1080 / 100 = 10.8 ≈ 11`

С учётом резервирования по формуле **N + 1**:

- `11 + 1 = 12`

Итого:

- **CDN cache / edge-серверы: 12 узлов**

### Итоговая таблица по оборудованию

| Контур | Уровень | Количество | Конфигурация узла | Формула резервирования |
|---|---|---:|---|---|
| Web/API | L4 | 2 | `CPU 8 cores, NIC 10GbE` | `N × 2` |
| Web/API | L7 | 2 | `CPU 16 cores, NIC 10GbE` | `N + 1` |
| CDN | Cache / Edge | 12 | `CPU 16 cores, NIC 100GbE` | `N + 1` |

## Часть 5. Логическая схема БД

### Выделение сущностей и хранилищ из текущей специфики

- **Пользовательский контур:** пользователь, настройки, учётные данные локальной авторизации, сессии/устройства.
- **Каталог:** единая сущность `ContentItem` для фильмов, сериалов, эпизодов и телеканалов; вложенность задаётся через `parent_content_id`.
- **Пользовательские действия:** избранное, прогресс просмотра, оценки, отзывы/рецензии.
- **Файловые данные:** постеры/изображения и видеопакеты HLS/DASH (manifests + segments).
- **Производные данные:** поисковый индекс, кэш карточек каталога, персональные рекомендации.
- **Буферы и edge-кэши:** буфер чекпоинтов прогресса и CDN-кэш сегментов.
- **Аналитический контур (`DWH`):** сырые события, измерения и агрегаты для продуктовой аналитики и расчёта рекомендаций.

Отдельную сущность `WatchHistory` в online-схеме не выделяю: для продуктового сценария достаточно хранить актуальный прогресс в `WatchProgress`, а полную событийную историю просмотра, клики по карточкам, поисковые запросы и показы рекомендаций логичнее уводить в отдельный аналитический контур.

- самая тяжёлая запись в API — сохранение прогресса просмотра (`~26.7k` peak write QPS), поэтому прогресс нельзя хранить только в одной «таблице без буфера»;
- каталог, поиск и рекомендации — основные read-heavy сценарии, поэтому у них должны быть отдельные производные хранилища;
- видео и постеры вынесены в файловые/object storage, потому что в сервисе это отдельный тяжёлый контур хранения и раздачи.

ER-диаграмма ниже покрывает только online-serving контур. `DWH` вынесен отдельно: туда выгружаются сырые события просмотров, поисков, кликов и взаимодействий с рекомендациями, а уже из агрегатов/фичей формируется `RecommendationCache`.

### Аналитический контур (`DWH`)

В этой работе `DWH` реализуется через `ClickHouse`, а не через отдельный набор OLTP-таблиц. Туда складываются сырые события и агрегаты, которые используются для аналитики и пересчёта рекомендаций, не нагружая основной online-контур.

Поток данных выглядит так:
`OLTP / API -> Kafka -> ClickHouse -> агрегаты / feature jobs -> RecommendationCache`

Минимальный набор таблиц в `ClickHouse`:
- `watch_events` — события просмотра: `start`, `heartbeat`, `stop`, `complete`;
- `search_events` — поисковые запросы и клики по результатам;
- `recommendation_events` — показы и клики по рекомендациям;
- `user_content_daily_agg` — суточная агрегация взаимодействий пользователя с контентом.

- `PostgreSQL` или аналогичная OLTP-БД хранит пользовательские и продуктовые online-данные;
- `ClickHouse` хранит историю событий и агрегаты;
- сервис рекомендаций читает агрегаты из `ClickHouse`, считает выдачу и записывает готовый top-N в `RecommendationCache`.

### 6.2 Денормализация

В физической схеме используются следующие денормализации:

1. `ContentCardCache` хранит готовую сериализованную карточку контента, чтобы каталог и главная страница не собирали её из OLTP-таблиц на каждый запрос.
2. `RecommendationCache` хранит уже рассчитанный `top-N` по пользователю.
3. `SearchIndex` дублирует текстовые поля и признаки ранжирования из `ContentItem`.
4. `UserContentDailyAgg` хранит дневные агрегаты по пользователю и контенту вместо повторного расчёта по сырым событиям.

| Хранилище | Что бэкапится | Схема |
|---|---|---|
| `PostgreSQL` | пользовательские данные, каталог, прогресс, оценки, отзывы, сессии | ежедневный full backup + WAL-архивирование, `PITR` |

| `S3 / MinIO` | постеры, manifests, сегменты | versioning + георепликация бакетов |
| `CDN / edge cache` | не бэкапится | полностью восстанавливается из `S3` origin |

### 6.8 Обоснование выбора физической схемы

1. `PostgreSQL` покрывает транзакционный контур, где критичны согласованность и обновления по пользователю.
2. Самая тяжёлая запись в системе изолирована в `PlaybackCheckpointBuffer`, поэтому OLTP не принимает десятки тысяч мелких checkpoint-записей напрямую.
3. Полнотекстовый поиск вынесен в отдельный search-кластер, чтобы не перегружать каталоговые таблицы.
4. `ClickHouse` получает асинхронные события через `Kafka`, поэтому аналитика и рекомендации не конкурируют с online-запросами.
5. Медиаобъекты физически отделены от OLTP и живут в `S3`, а пик раздачи сегментов уходит в `CDN`.

## Часть 7. Алгоритмы

В данном разделе рассматриваются только те алгоритмы, реализация которых напрямую влияет на архитектуру сервиса, выбор хранилищ и профиль нагрузки.

### 7.1 Рекомендательная система: Content-Based Filtering + Cosine Similarity

Для персональных рекомендаций используется **content-based filtering**.  
Идея алгоритма состоит в том, что пользователю предлагаются тайтлы, близкие к уже просмотренному и высоко оценённому контенту.

Для этого для пользователя строится профиль интересов по жанрам и ключевым персонам (актёрам, режиссёрам), а для каждого тайтла — его контентный профиль.  
Далее близость пользователя и тайтла оценивается через **cosine similarity**. Отдельно считаются близость по жанрам и близость по персонам, после чего итоговый вес определяется как их взвешенная комбинация:

`content_score = (cos_sim_genre + alpha * cos_sim_person) / (1 + alpha)`

где `alpha` — коэффициент значимости персон относительно жанров.  
Возьмем `alpha = 1.5`: жанры остаются базовым признаком, но совпадение по актёрам и режиссёрам усиливает рекомендацию.

Далее итоговый recommendation score рассчитывается как:

`final_score = 0.7 * content_score + 0.3 * popularity_score`

где `popularity_score` — поправка на общий интерес аудитории к тайтлу.  
Популярность получает меньший вес, чтобы рекомендации оставались персональными, а не превращались просто в список самых популярных фильмов платформы.

Сырые события просмотров, поисков, кликов и оценок сначала отправляются в `Kafka`, затем сохраняются в `ClickHouse`. После этого recommendation worker периодически пересчитывает признаки и кандидатов, сохраняет durable snapshot в `RecommendationCandidateStore Cassandra` и горячую персональную выдачу в `RecommendationCache Redis`. При online-запросе `Recommendation API` берёт кандидатов из кэша или snapshot-а, а `OnlineRanker` дополнительно учитывает свежие действия пользователя.

### 7.2 Сохранение прогресса просмотра: Monotonic Merge / Coalescing

Во время воспроизведения клиент раз в 30 секунд отправляет checkpoint с текущей позицией просмотра.  
Если записывать каждый такой checkpoint напрямую в `PostgreSQL`, это создаст слишком большую write-нагрузку на транзакционный контур.

Поэтому сохранение прогресса выделяется в отдельный `Playback / Progress` контур.  
`Progress Service` сразу обновляет горячее состояние в `HotProgressCache Redis` и публикует checkpoint-событие в `Kafka`:

`Progress Service → HotProgressCache Redis`  
`Progress Service → Kafka playback.progress.checkpoints → ProgressWriter → Cassandra PlaybackProgressStore`

Для промежуточных checkpoint-ов используется алгоритм **coalescing** — коалессация промежуточных записей.  
Для ключа `(user_id, content_id, device_id)` хранится последнее актуальное значение прогресса. Обновление выполняется по правилу **monotonic merge**:

`progress_new = max(progress_old, progress_checkpoint)`

То есть прогресс для продолжения просмотра двигается вперёд и не создаёт поток append-only записей.  
`ProgressWriter` батчами обновляет durable-хранилище `Cassandra PlaybackProgressStore`, где хранятся таблицы прогресса по пользователю и контенту.

`Redis` в этом контуре не является durable-хранилищем, а используется только как hot cache последних checkpoint-ов.  
Если `Redis` недоступен или произошёл cache miss, `Progress Service` читает последнее durable-состояние из `Cassandra`.

Такой подход снижает write-нагрузку на `PostgreSQL`, позволяет сглаживать пики checkpoint-событий через `Kafka` и сохраняет основной пользовательский сценарий — продолжение просмотра с последнего сохранённого места.

### 7.3 Раздача видео: Adaptive Bitrate (ABR) + Greedy Profile Selection

Для видеоконтента используется **adaptive bitrate streaming**.  
Видео хранится в `MediaPackageStore` в виде manifests и сегментов нескольких bitrate-профилей. После получения manifest клиент оценивает доступную полосу сети и выбирает подходящий профиль качества.

Выбор профиля выполняется по жадному правилу (**greedy profile selection**): выбирается максимальный профиль, который можно воспроизводить устойчиво при текущей полосе пропускания:

`R_selected <= k * B_available`

где:
- `R_selected` — выбранный битрейт потока;
- `B_available` — оценка доступной полосы клиента;
- `k < 1` — коэффициент запаса.

Коэффициент запаса нужен для того, чтобы избежать частых переключений качества и буферизации при небольших колебаниях сети.

Далее раздача сегментов строится иерархически:
1. клиент запрашивает сегмент у ближайшего edge-узла CDN;
2. при cache hit сегмент отдаётся сразу;
3. при cache miss сегмент забирается из origin-хранилища `MediaPackageStore` и затем может быть закэширован на edge-узле.

Таким образом, горячие сегменты и популярные тайтлы обслуживаются в основном через `CDN`, а origin используется только как исходный источник. Это уменьшает нагрузку на центральное медиахранилище и позволяет поддерживать стабильное воспроизведение даже при нестабильном соединении пользователя.

## Часть 9. Обеспечение надёжности

Основной принцип: критичные пользовательские сценарии должны продолжать работать в деградированном режиме, а производные состояния — поиск, кэши, рекомендации, аналитика — должны восстанавливаться из источников истины.

| Риск / отказ | Архитектурное изменение | Как работает при отказе | Эффект для пользователя |
|---|---|---|---|
| Перегрузка контура сохранения прогресса просмотра | Выделен отдельный `Playback / Progress` контур: `Progress Service → Kafka playback.progress.checkpoints → ProgressWriter → Cassandra PlaybackProgressStore`; `Redis` используется как `HotProgressCache` | Частые checkpoint-события не пишутся напрямую в `PostgreSQL`. `Kafka` сглаживает поток, а `ProgressWriter` батчами обновляет `Cassandra`. При пике очередь накапливает события, а не валит OLTP-БД | Просмотр видео не ломается при всплеске нагрузки. Возможна задержка обновления позиции, но пользователь не теряет доступ к контенту |
| Потеря нескольких последних checkpoint-ов | Для прогресса используется eventual consistency: `Cassandra` хранит durable-состояние, `Redis` — горячее состояние текущей сессии | Если часть checkpoint-ов потеряна, система откроет фильм или серию с последней durable-сохранённой позиции | Пользователь максимум начнёт просмотр на несколько секунд раньше или позже, но сервис продолжит работать |
| Отказ `Redis HotProgressCache` | Read path устроен как `Redis → Cassandra fallback` | `Redis` не является источником истины. При отказе `Redis` `Progress Service` читает прогресс из `Cassandra`, а после восстановления кэш постепенно прогревается заново | Старт фильма или серии может стать чуть медленнее, но прогресс просмотра остаётся доступен |
| Отставание или потеря событий индексации каталога | Добавлены `Catalog Outbox`, `SearchIndexer`, `FallbackSearchIndexWorker` и `Search Reconciliation Job` | При изменении фильма или серии запись фиксируется в `Catalog DB` и `catalog_outbox` в одной транзакции. `Catalog Outbox Publisher` отправляет `catalog.content.updated` в `Kafka`. `SearchIndexer` обновляет `OpenSearch`, а `FallbackSearchIndexWorker` обновляет fallback read model. `Search Reconciliation Job` периодически сверяет версии и чинит пропуски | Новый или изменённый контент появляется в поиске даже при временном сбое worker-а или consumer-а |

| Отказ recommendation pipeline или задержка пересчёта рекомендаций | Рекомендации разделены на offline и online части: `ClickHouse → Aggregation Jobs → Recommendation Training / Candidate Worker → RecommendationCandidateStore Cassandra / RecommendationCache Redis`; отдельно используются `OnlineRanker` и `FallbackFeedCache` | Если персональные рекомендации в `Redis` недоступны, `Recommendation API` берёт stale candidates из `Cassandra`. Если персонального snapshot-а нет, используется неперсональный fallback feed: популярное, новинки, топ по жанрам | Главная страница не пустая. Пользователь получает менее персонализированную, но рабочую выдачу |
| Потеря событий просмотров, кликов и показов | Все клиентские события идут через `Event Collector API → Kafka → Analytics Consumers → ClickHouse`; consumers идемпотентные, ошибки после retry уходят в `DLQ` | При временной ошибке `ClickHouse` или consumer-а событие повторяется. Если обработка невозможна после N retry, событие попадает в `DLQ topic` и может быть переобработано через `DLQ Reprocessor` | Аналитика и рекомендации могут обновиться позже, но основной просмотр, каталог и карточки не падают |
| Некорректное смешение факта выдачи рекомендаций и факта клика | `Recommendation API` пишет только `recommendation.served.events`, а реальные клики, показы и просмотры идут с фронта через `Event Collector API` | Backend фиксирует факт выдачи списка, а frontend фиксирует фактическое поведение пользователя | Данные для аналитики и рекомендаций становятся корректнее: система различает “рекомендация была выдана” и “пользователь реально увидел или кликнул” |
| Каскадный отказ внутренних сервисов | `timeouts`, `retry budget`, `circuit breaker` и `rate limits` настроены на уровне `L7 API Gateway / NGINX`, а не как отдельные сервисы перед каждым микросервисом | Если `Search`, `Recommendation` или `UserActivity` начинают отвечать медленно, Gateway ограничивает обращения и включает degraded response | Один зависший сервис не утягивает весь API. Карточка фильма или главная страница открываются в урезанном режиме |
| Отказ блока отзывов и рейтингов | `Movie Page Composition / BFF` умеет отдавать core content card без social-блока | Если `UserActivity Service` недоступен, BFF не ждёт его бесконечно и возвращает карточку фильма без отзывов и рейтингов | Пользователь может открыть карточку и начать просмотр, хотя отзывы и рейтинг временно скрыты |
| Отказ части CDN edge | CDN edge cache считается расходуемым слоем, origin хранится в `S3-compatible Object Storage` | При отказе edge-узла трафик уходит на другой edge. При cache miss постер, статика, manifest или video segment подтягиваются из object storage origin | Может вырасти latency или снизиться hit ratio, но медиаобъекты не теряются |
| Отказ object storage origin или риск потери медиа | `S3-compatible Object Storage` используется как durable origin для `poster_image_store`, `static_assets`, `media_package_store`, `HLS/DASH manifests`, `video segments origin`; для него подразумеваются versioning, replication и backup-политики | При проблеме с edge-кэшем данные восстанавливаются из origin. При логической или физической проблеме origin восстанавливается из версий, репликации или backup | Пользователь может столкнуться с временной деградацией выдачи медиа, но контент не считается потерянным |
| Логическая ошибка при обновлении каталога | `Catalog DB` остаётся master-источником, а `OpenSearch`, `Redis cache` и `FallbackSearchReadModel` считаются производными хранилищами | При ошибке исправляется или откатывается master-состояние в `Catalog DB`, после чего производные индексы и кэши пересобираются через outbox, reconciliation и cache invalidation | Исправляется источник истины, а поисковые индексы и кэши догоняются автоматически |
| Отказ auth-контура | Auth считается критическим сценарием. Сессии лежат в `Redis SessionStore`, credentials — в `Auth DB PostgreSQL`; для уже выданных валидных токенов возможна работа в пределах TTL | Новые логины могут быть ограничены, но уже авторизованные пользователи с валидным токеном не разлогиниваются мгновенно | Массовый мгновенный разлогин не происходит, но новые auth-операции могут быть временно ограничены |
| Ошибки асинхронных worker-ов | Для `SearchIndexer`, `FallbackSearchIndexWorker`, `ContentCacheInvalidationWorker`, `ProgressWriter`, `AnalyticsConsumer`, `RecentActivityConsumer`, `Recommendation jobs` используются retry, идемпотентность и `DLQ` | Временные сбои обрабатываются retry. Неразобранные события уходят в `DLQ topic`, затем могут быть переобработаны через `DLQ Reprocessor` | Система деградирует по задержке обновления индексов, аналитики и рекомендаций, а не по доступности основного продукта |
| Зависание или отставание outbox publisher-ов | `Catalog Outbox Publisher` и `UserActivity Outbox Publisher` повторно читают неопубликованные строки outbox и помечают `published_at` только после успешной публикации | Если publisher временно упал, outbox-строки остаются неопубликованными и будут отправлены после восстановления | Изменения каталога и пользовательские действия не теряются как события; они доезжают позже |
| Отказ `RecentUserActivityCache` | Свежие действия пользователя хранятся в `RecentUserActivityCache Redis`, но рекомендации могут работать по stale candidates и fallback feed | Если recent cache недоступен, `OnlineRanker` теряет часть свежего контекста, но `Recommendation API` может использовать durable candidates из `Cassandra` или fallback feed | Рекомендации становятся менее точными, но блок рекомендаций остаётся рабочим |

### Инфраструктурный фон

Помимо архитектурных механизмов выше, для базовой отказоустойчивости используются стандартные инфраструктурные меры:

- `GeoDNS / Weighted GSLB` с health checks и коротким TTL для переключения трафика между регионами;
- несколько экземпляров stateless backend-сервисов за `L7 API Gateway`;
- резервирование `L4` и `L7` балансировщиков;
- репликация и backup для `PostgreSQL`, `Cassandra`, `ClickHouse` и `S3-compatible Object Storage`;
- кластерный режим для `Kafka`, `Redis`, `OpenSearch`;
- мониторинг, алерты и health checks для ключевых пользовательских сценариев.

## Часть 10. Схема проекта

![Архитектурная схема](images/scheme.png)
 
Сплошные стрелки обозначают синхронные запросы, оранжевые пунктирные — асинхронные события через `Kafka`, красные пунктирные — fallback/degraded path, серые пунктирные блоки — пояснения, локальные входы или ссылки на компоненты из других доменов.

Схема разделена на несколько доменов:

- `Global routing / entry` — разделяет API-путь и CDN-путь. API-запросы идут через `GeoDNS / Weighted GSLB → L4 → L7 API Gateway`, а медиа и статика идут через `Anycast CDN routing → CDN Edge Cache`.
- `User / Auth domain` — отвечает за авторизацию, сессии, профиль пользователя и регистрацию.
- `Catalog / Search domain` — хранит master-данные каталога, обновляет `OpenSearch`, поддерживает fallback-поиск и repair-процессы.
- `Playback / Progress domain` — отвечает за старт просмотра и сохранение прогресса через `Kafka`, `ProgressWriter`, `Cassandra` и `Redis HotProgressCache`.
- `Content Page Composition + User Activity domain` — собирает карточку фильма и обрабатывает избранное, рейтинги и отзывы.
- `Event / Analytics + Kafka domain` — собирает клиентские и backend-события, передаёт их в `Kafka`, `ClickHouse`, consumers и `DLQ`.
- `Recommendation / Analytics domain` — строит offline-кандидатов, выполняет online ranking и содержит fallback feed.
- `Media / CDN domain` — хранит origin-медиа в `S3-compatible Object Storage` и отдаёт постеры, статику и видео через CDN.

`Kafka topic port` внутри отдельных доменов — это локальные визуальные входы в один общий `Kafka Event Bus`. Такой формат нужен, чтобы не тянуть через всю схему большое количество длинных пересекающихся стрелок, но при этом сохранить явные producer/consumer-потоки.

1. `WatchProgress` вынесен из `PostgreSQL` в `Cassandra`; `Redis` используется как hot cache, а не как durable-хранилище.
2. Для каталога добавлен `Catalog Outbox`, чтобы не терять события обновления контента.
3. Для поиска добавлены `SearchIndexer`, `FallbackSearchReadModel` и `Search Reconciliation Job`.
4. Пользовательские события идут с фронта через `Event Collector API`, а `Recommendation API` пишет только факт выдачи рекомендаций.
5. Для поиска, рекомендаций, прогресса и карточки фильма показаны fallback-сценарии.
